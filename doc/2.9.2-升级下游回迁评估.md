# 2.9.2 升级下游问题回迁评估

> 目的：汇总 2.9.x 升级的反向验证中下游应用暴露的问题，识别哪些属于**共享框架缺陷/能力缺口**、
> 应回迁到 `eap-common`（及 `eap-boot`），并按“最小影响”原则在 2.9.2 内落地。
>
> 验证方式：由多个下游应用在真实升级窗口（2026-08-28 ~ 2026-09-15）内适配 JDK 17 + Spring Boot 3.5.16 基线，
> 其升级改动与线上问题作为输入；本文只保留可复用的框架侧结论，不记录具体应用与业务信息。
>
> 结论口径：能由 BOM/Starter 一处收敛的，回迁；纯业务/应用依赖选择的，保留在应用侧并在本文档说明。
>
> 面向升级操作的简明版见 [升级指南](升级指南.md)（版本矩阵、升级步骤、下游注意事项）。

## 一、升级事实基线

| 下游形态 | 升级动作 | 暴露问题 |
| --- | --- | --- |
| 使用 BOM + eap-boot 模块类制品 | eap 2.8.1 → 2.9.1（Spring Boot 3.5.16 / Spring Cloud 2025.0.1 / MyBatis-Plus 3.5.16 / jsqlparser 暂留 4.9） | 依赖树断裂、三方工具类消失、动态 SQL API 差异 |
| 仅使用 BOM + `eap-spring-boot-starter-*` | Spring Boot 3.4.12 → 3.5.16、eap-boot 2.8.1 → 2.9.1c | RabbitMQ 反序列化失败、POI 死坐标解析失败、Connector/J DATETIME 强转异常 |
| 升级后修复（9 月） | RabbitMQ 反序列化、Redis pending 死循环、动态 SQL 列裁剪 | 均为升级后运行期暴露，非编译期 |

升级本身于 2026-08-30 ~ 09-01 落地，9 月为运行期问题修复期，因此评估范围覆盖该窗口。

## 三、2.9.2 已实施变更

### 3.1 eap-common / starter-mq：可信根包类型映射器

- 新增 `org.openea.eap.framework.mq.rabbitmq.core.TrustedRootJackson2JavaTypeMapper`。
- 修改逻辑：在父类 `DefaultJackson2JavaTypeMapper` 做可信包校验前，把消息头中出现的**精确包名**动态登记进可信集合，
  用一个根包（如 `org.openea.eap`）覆盖其下所有子包。
- 修改原因：Spring AMQP 自 3.2.11 起（Boot 3.5.16 → spring-amqp 3.2.12）把无参转换器默认可信包由 `*` 收紧为
  `[java.util, java.lang]`；而 `isTrustedPackage` 只做包名精确相等判断，不支持父包前缀/通配，逐个枚举包名必然复发。
- 影响面：纯新增类，不改变 starter 默认行为；应用不使用时零感知。单测覆盖放行/拒绝/内置 java 包/前缀边界/转换器端到端。
- `readme.md` 增补“根包覆盖子包”推荐写法与 `@Primary` 约定。

### 3.2 eap-common / eap-dependencies：POI 死坐标

- `poi-ooxml-schemas` 由 `${poi.version}=5.4.0` 改为独立的 `${poi-ooxml-schemas.version}=4.1.2`（该构件最后一个真实版本）。
- 原因：POI 5.x 起不再发布 `poi-ooxml-schemas`（改由 `poi-ooxml-full/lite` 承载），原管理项指向不存在的坐标；
  `easypoi-base` 4.4.0 显式依赖该构件但未声明版本，会取到 BOM 的死坐标导致解析失败——这正是升级实践中
  下游被迫在应用侧整体钉版 POI 家族 4.1.2 的根因。
- 保持 `poi`/`poi-ooxml` 仍为 5.4.0：`easyexcel-core` 4.0.3 明确依赖 POI 5.2.5，不能整体降级。
- 范围界定：本修正只消除“坐标不存在”造成的**解析失败**；仍在 `easypoi` 4.x 上的应用若需要 POI 4.x 运行时，
  应继续在应用侧自行钉版 POI 家族——那属于应用依赖选择，不是 BOM 缺陷。
- 影响面：eap-common / eap-boot 自身不使用该构件，零影响。

### 3.3 eap-common：版本一致性

- `eap-dependencies/pom.xml`、`eap-cloud-dependencies/pom.xml` 的 `<revision>` 由 2.9.1c 升到 2.9.2。
- 原因：二者为 standalone pom（无 parent），不继承根 pom 的 `${revision}`；根 pom 以 `${revision}` 导入这两个 BOM，
  版本不同步会让 reactor 同时出现两个版本，`mvn` 在读取 POM 阶段即报 `Non-resolvable import POM`。
- 影响面：仅版本号；`eap-boot` 同步升到 2.9.2 后方可消费。

### 3.4 eap-boot：版本标识对齐

- 根 pom `revision` 升到 2.9.2；`eap-gateway/src/main/resources/application.yaml` 的 `eap.info.version`、
  `doc/技术架构分析.md` 的“基础框架”版本同步为 2.9.2。
- 本仓无框架级代码改动需求：`ApiErrorLogApiImpl` 已在 2.9.1 对齐 `ApiErrorLogCommonApi`，且不使用
  `poi-ooxml-schemas`、未自定义 RabbitMQ `MessageConverter`，本次 BOM/Starter 变更对其零行为影响。

### 3.5 文档

- eap-common README 版本徽标、示例配置、文档版本，`doc/技术架构分析.md` 项目版本同步到 2.9.2。
- 新增升级指南与发布记录（`CHANGELOG.md`），并分别在两仓 AGENTS 中固化“版本变更同步文档”的规则。

## 四、jsqlparser 4.9 兼容配方（不回迁代码，仅固化用法）

应用若因直接使用 jsqlparser 4.x API 而需要停留在 4.9，按以下顺序操作即可，无需改动 eap-common：

1. 在应用根 POM `dependencyManagement` 中：
   - 钉 `com.github.jsqlparser:jsqlparser:4.9`（覆盖 `mybatis-plus-jsqlparser` 传递的 5.x）；
   - `mybatis-plus-jsqlparser-4.9` **无需声明版本**：`eap-dependencies` 已通过 `mybatis-plus-bom` 将其管理到
     `${mybatis-plus.version}`；
2. 排除 `eap-spring-boot-starter-mybatis` 传递的默认适配器 `mybatis-plus-jsqlparser`（按 jsqlparser 5.x 编译，
   与 4.9 混用会在分页/多租户拦截器运行期 `NoSuchMethodError`，且与 4.9 适配器存在同名类）；
3. 在应用启动模块显式引入 `mybatis-plus-jsqlparser-4.9`。

> 注：4.9 的 `SelectBody`/`getSelectBody`/`SubSelect` 为 deprecated 但未移除；`ParenthesedSelect` 包装对象
> 需取 `getSelect()` 再判断 `PlainSelect`，直接对包装对象做 `instanceof PlainSelect` 会静默不裁剪。

## 五、建议后续版本处理（本次不动）

**总体优化思路：优先跟随主流，再兼容已明确问题。**

1. **版本与依赖跟随官方**：Spring Boot / Spring Data Redis / Spring AMQP / MyBatis-Plus 的版本与默认行为以官方 BOM 为准；
   旧驱动、旧 POI、旧 jsqlparser 只作为**应用侧短期过渡**，不作为框架默认（本版 POI 修复即体现：修死坐标，但不整体降级）。
2. **默认值取官方默认**：框架不主动偏移所有消费者的运行语义（如不默认注入 `treatMysqlDatetimeAsTimestamp`）。
3. **兼容行为用具名开关提供**：当官方默认会破坏“已明确问题”中的存量行为时，提供显式属性，**默认关闭**，由应用按需开启。
4. **可观测 + 可回退 + 免数据迁移**：语义变更必须能通过日志/指标定位、能通过开关回退，且不需要存量数据迁移。
5. **与相邻框架去重**：相邻框架已提供的兼容能力（如 DATETIME 注入）不做第二套实现。

### 5.1 Redis Stream 重投死循环治理

- **主流做法**：消费者组用 PEL + `XCLAIM` 重新投递（保留原消息 id，delivery count 递增）；
  失败重试设上限，超限进死信 stream；容器统一配置
  `StreamMessageListenerContainerOptions.errorHandler(ErrorHandler)` 记录异常。
  （已核实本版 Spring Data Redis 4.1 同时提供 `errorHandler(...)`、`StreamOperations#claim(...)` 与
  `PendingMessage#getTotalDeliveryCount()`；`XAUTOCLAIM` 在当前 Spring Data Redis 未直接暴露，暂不作为依赖项。）
- **已明确问题**：`AbstractRedisStreamMessageListener#onMessage` 异常时不 ack、无 catch；
  `RedisPendingMessageResendJob` 是“复制成新记录 + ack 老记录”，因此 delivery count 不增长，
  业务持续失败时每 5 分钟复制一次、永不终止，并把已完成任务误标为异常。
- **兼容落地**：
  - 重投机制由“复制”切换为 `claim`（同一消息 id 重投；下游业务侧已有的幂等短路继续生效，不要求业务改造）；
    这一步属机制对齐、对正常链路语义等价，可默认启用。
  - 上限与死信**默认关闭**（`eap.mq.redis.stream.max-delivery=0` 表示不限，等同现状），由应用显式开启；
    新项目建议值 16。开启后超限消息先写入 `{stream}:dead` 再 ack，写死信失败则不 ack，保证不静默丢弃。
  - 配置 `errorHandler`，把 stream key、record id、异常堆栈打全，替代当前“异常冒泡后只剩业务日志”的状态。
- **验收**：正常消息 ack 行为不变；开启上限后重投次数可见且封顶；下游业务侧幂等短路相关单测保持通过；存量 PEL 无需迁移即可继续处理。

### 5.2 MySQL DATETIME / Connector-J 兼容

- **主流做法**：驱动跟 Spring Boot BOM（Connector/J 9.x）；时间类型用 `java.time`（`LocalDateTime`/`Instant`）映射，
  遵循 JDBC 4.2 语义；确需兼容旧 `java.util.Date` 时使用官方连接参数 `treatMysqlDatetimeAsTimestamp=true`，
  **而不是降级驱动**。
- **已明确问题**：Connector/J ≥ 8.0.23 对 DATETIME 的 `getObject()` 返回 `LocalDateTime`，存量 `(Date) map.get(...)`
  抛 `ClassCastException`；升级期出现过临时降级到 8.0.21 的做法，并因此产生“新坐标 `com.mysql:mysql-connector-j`
  + 8.0.21”这类在任何仓库都不存在的坐标组合，导致解析失败。
- **兼容落地**：
  - 版本上不做降级、不管理旧坐标（`mysql:mysql-connector-java` 不再进 BOM），驱动版本完全交给 Boot BOM。
  - `treatMysqlDatetimeAsTimestamp` 若由框架提供，必须与相邻框架已有的兼容注入**共用同一入口**，
    避免重复注入；属性形如 `eap.datasource.mysql.treat-datetime-as-timestamp`，**默认 false**（即官方默认 LocalDateTime），
    由存量应用显式开启。
  - 新代码规范用 `java.time`；存量 `(Date)` 强转按模块逐步改造，不要求一次性全量改写。
- **验收**：开关开启时 Map/JdbcTemplate 取 DATETIME 仍返回 `Timestamp`；关闭时返回 `LocalDateTime`；
  默认数据源与动态数据源行为一致；与相邻框架注入不冲突。

### 5.3 停止整体拷贝 `EapWebAutoConfiguration`

- **主流做法**：自动配置应“默认可用 + 可增量覆盖”——Bean 方法加 `@ConditionalOnMissingBean`，
  用 `@AutoConfiguration(before/after)` 控制装配顺序；应用自定义消息转换器只需注册 `HttpMessageConverter`
  Bean（Boot 会与默认转换器合并），无需整类覆盖。
- **已明确问题**：有下游应用以同 FQCN 覆盖 starter 类做 fastjson 定制，升级时因
  `GlobalExceptionHandler` 构造参数由 `ApiErrorLogApi` 改为 `ApiErrorLogCommonApi`，被迫额外手工同步；
  一旦漏改，编译失败或行为不一致，且问题定位困难。
- **兼容落地**：
  - 框架侧为 starter-web 的 Bean 增加 `@ConditionalOnMissingBean`：对未覆盖的应用零影响、向后兼容，可默认启用。
  - 应用侧迁移为增量 Bean；迁移期允许保留拷贝，但要求“上游签名变更时编译即暴露”，避免静默漂移。
  - 落地前复核：`HttpMessageConverters` 在 Spring Boot 3.5.16 尚未废弃（已核实），
    但仅自定义 fastjson 时应注册单个 `HttpMessageConverter`，不要定义 `HttpMessageConverters` 全量替换默认转换器。
- **验收**：移除应用拷贝后，路径前缀、CORS、RequestBody 缓存、异常处理与消息转换行为不变；
  应用自定义转换器仍能在响应中生效。

## 七、下游可选的简化（本次未改下游仓库）

- 若应用中已自行实现同类“可信根包”类型映射器，可切换为 starter 提供的
  `org.openea.eap.framework.mq.rabbitmq.core.TrustedRootJackson2JavaTypeMapper`。
- 仅为规避 POI 解析失败的强制钉版可去除；若仍使用 `easypoi` 4.x，运行时钉版保留即可。
- 应用侧 eap 版本属性升到 2.9.2 后，即可获得 `@ConditionalOnMissingBean` 转换器退让与新映射器。
