# 分支与发布策略

| 分支 | 职责 | 开发版本 | Java / Spring Boot |
| --- | --- | --- | --- |
| `dev` | 3.x 主干开发，PR 默认目标 | `3.0.1-SNAPSHOT` | JDK 21 默认、JDK 25 兼容 / Boot 4.1.2 |
| `2.x` | 安全、兼容修复及少量审慎功能，2.x PR 目标 | `2.9.4-SNAPSHOT` | Java 17 / Boot 3.5.16 |
| `main` | 当前正式发布基线，暂保留 2.9.3.1 | 正式版 | 首个 3.x 正式发布时再切换 |
| `boot4` | 迁移前历史分支，已冻结，不再接收开发 | 历史快照 | 变更已合并到 dev；保留用于追溯 |

## 开发与修复

- 两仓始终使用配套版本：2.x 配 2.x，dev 配 dev；禁止交叉使用本地 Maven 缓存中的同名制品。
- 在受影响分支修复，再以独立 PR/cherry-pick 按需移植到另一条线；迁移完成后不再整体互相合并 2.x 与 dev。
- 2.x 不引入 Java 21、Boot 4 或破坏性接口改动。3.x 继续保留认证边界、旧 Redis Key 读取、JWT 唯一性与依赖安全补丁。
- PR 页面默认目标仍为 dev；维护修复必须显式选择 2.x。CI 按 PR 目标分支选择 JDK。

## 发布

- 2.x 下一版为 2.9.4：在 2.x 准备正式 revision 和发布记录，使用固定的 40 位 SHA 和 `v2.9.4` 标签（或当时 2.x HEAD）执行发布；发布成功后再推进 2.9.5-SNAPSHOT。
- 允许四段紧急补丁版本；旧版本补丁应从对应不可变版本标签建立发布候选，更新 revision 后创建新标签，不覆盖已有 GAV。
- 顺序为 common build-only → common 正式发布及 Central 验证 → boot build-only → boot 正式发布及 Central 验证。
- dev/boot4 和所有 3.x 坐标当前只允许 build-only，不能因本次分支迁移发布到 Central。3.x 首次正式发布需另行审核发布门槛，并决定 main 切换。
- 受控发布入口为 eaopen/eap-release；保留源码 SHA 固定、制品完整性检查、独立签名及发布身份限制。
- 分支迁移不代表业务部署验收；生产环境、数据库、Redis 数据与下游应用不随本次迁移改动。

## 验证

使用对应 JDK，先构建 common，再构建 boot。指定每条线独立的 `-Dmaven.repo.local`。
common 首次验证先分别安装两个独立 BOM，然后执行 `mvn -Pcloud,dev clean install`。
boot 使用同一缓存及独立 Redis，执行 `mvn -Pcloud,dev -Dspring.data.redis.port=<测试端口> clean install`。
检查运行包实际依赖并执行 `script/verify-jwt-runtime/verify.py`，不要仅凭 POM 声明认定兼容。

## 3.x 的 JDK 21/25 兼容

默认开发、发布 JDK 为 21；JDK 25 可构建和运行。`java.version` 与 `maven.compiler.release` 保持 21，避免新 JDK API 意外进入 Java 21 制品。dev 的 CI 同时执行 JDK 21 与 25，全量测试和打包均须通过；2.x CI 保持 JDK 17。发布控制器仍使用 JDK 21，不因兼容验证改变正式制品基线。
